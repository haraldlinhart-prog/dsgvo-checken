HTTPS-Weiterleitung funktioniert nicht: Ursachen finden und aus DSGVO-Sicht richtig einordnen

Sie haben ein SSL-Zertifikat installiert, doch beim Aufruf der Adresse mit „http://“ landen Besucher weiterhin auf der unverschlüsselten Seite. Oder der Browser meldet eine Umleitungsschleife. Wenn die HTTPS-Weiterleitung nicht funktioniert, ist das mehr als ein Schönheitsfehler: Daten werden womöglich unverschlüsselt übertragen. Dieser Beitrag zeigt, woran es meistens liegt und wie Sie systematisch vorgehen.

Warum die Weiterleitung auch datenschutzrechtlich relevant ist

Die DSGVO verlangt, dass personenbezogene Daten mit angemessenen technischen Maßnahmen geschützt werden. Auf Websites ist die Transportverschlüsselung dafür eine Grundvoraussetzung. Kontaktformulare, Login-Bereiche, Newsletter-Anmeldungen und selbst IP-Adressen in Server-Logs sind betroffen. Ist nur das Zertifikat vorhanden, aber die Umleitung fehlt, können Nutzer über alte Links, Lesezeichen oder Suchergebnisse weiterhin die unverschlüsselte Variante erreichen. Genau solche Lücken fallen bei einer automatisierten Prüfung auf. Ob das im Einzelfall einen Verstoß darstellt, hängt von den konkreten Umständen ab; als Mangel sollten Sie es in jedem Fall beheben.

Erst prüfen, dann ändern: So grenzen Sie das Problem ein

Alle Varianten der Adresse testen

Rufen Sie nacheinander http://domain.de, http://www.domain.de, https://domain.de und https://www.domain.de auf. Jede Variante sollte am Ende bei genau einer bevorzugten HTTPS-Adresse landen. Häufig ist nur eine der vier Varianten betroffen, zum Beispiel die Version ohne „www“.

Cache und Browser ausschließen

Browser speichern Weiterleitungen teilweise zwischen. Testen Sie im privaten Fenster oder mit einem anderen Gerät. Leeren Sie außerdem Caches von Caching-Plugins, Server und Content-Delivery-Network (CDN), bevor Sie Schlüsse ziehen.

Den Weiterleitungsweg ansehen

Mit den Entwicklertools des Browsers (Reiter „Netzwerk“) oder einem Kommandozeilenaufruf mit Header-Ausgabe sehen Sie, welcher Statuscode zurückkommt und wohin verwiesen wird. Üblich ist eine dauerhafte Weiterleitung (301) auf die HTTPS-Adresse. Fehlt sie, greift keine Regel; sehen Sie viele Sprünge hintereinander, kollidieren mehrere Regeln.

Häufige Ursachen

Regel fehlt oder steht an der falschen Stelle

Bei Apache-Servern steht die Umleitung meist in der .htaccess-Datei, bei Nginx in der Server-Konfiguration. Liegt die Regel hinter einer anderen, die bereits greift, oder wird die Datei gar nicht ausgewertet, passiert nichts. Bei Nginx wird oft vergessen, den Server-Block für Port 80 mit einer Umleitung zu versehen.

Redirect-Schleife durch Proxy oder CDN

Läuft die Seite hinter einem CDN oder Reverse Proxy, erreicht den eigenen Server die Anfrage womöglich nur noch per HTTP. Der Server „sieht“ dann kein HTTPS, leitet um, das CDN fragt erneut per HTTP an – und es entsteht eine Schleife. Die Lösung liegt meist darin, den Verschlüsselungsmodus des CDN passend einzustellen und die Serverregel so zu formulieren, dass sie den vom Proxy gemeldeten Protokollhinweis auswertet.

Konflikte im CMS

Bei WordPress und ähnlichen Systemen sind Website- und Startadresse in den Einstellungen oft noch mit „http://“ hinterlegt. Dann leitet das System selbst zurück auf HTTP, während die Serverregel auf HTTPS umleitet. Auch Plugins zur Erzwingung von HTTPS können sich mit manuellen Regeln überschneiden. Nutzen Sie nur einen Mechanismus.

Mixed Content

Selbst wenn die Weiterleitung klappt, werden manchmal Bilder, Skripte oder Schriften weiterhin über HTTP eingebunden. Browser blockieren das teilweise oder warnen vor „nicht sicher“. Ursache sind meist fest eingetragene alte Adressen in Inhalten, Themes oder Datenbank. Diese müssen auf HTTPS oder relative Pfade umgestellt werden.

Zertifikat unvollständig

Deckt das Zertifikat die „www“-Variante oder eine Subdomain nicht ab, erscheint vor der Weiterleitung eine Browserwarnung. Auch abgelaufene Zertifikate oder fehlende Zwischenzertifikate führen dazu, dass die Umleitung scheinbar ins Leere läuft.

Hosting-Einstellungen

Viele Anbieter haben im Kundenbereich eine eigene Option für die HTTPS-Erzwingung. Sie kann mit eigenen Regeln kollidieren. Prüfen Sie dort zuerst, bevor Sie Dateien bearbeiten.

Sauber lösen: Vorgehen in der Praxis

  • Legen Sie eine bevorzugte Adresse fest (mit oder ohne „www“) und leiten Sie alle anderen Varianten in einem einzigen Schritt dorthin.
  • Sichern Sie vor Änderungen an Serverdateien eine Kopie, damit Sie bei einem Fehler zurückgehen können.
  • Stellen Sie die Adressen im CMS auf HTTPS um und ersetzen Sie alte HTTP-Verweise in den Inhalten.
  • Prüfen Sie nach der Änderung erneut alle vier Adressvarianten und mehrere Unterseiten.
  • Erwägen Sie, den Browsern zusätzlich per HSTS-Header mitzuteilen, dass die Seite nur über HTTPS aufgerufen werden soll. Setzen Sie das erst, wenn alles stabil läuft, da Fehler dann länger nachwirken können.

Auswirkungen auf Sichtbarkeit und Vertrauen

Eine fehlerhafte Umleitung kann dazu führen, dass Suchmaschinen dieselben Inhalte unter mehreren Adressen sehen. Nutzer verunsichert die Warnung im Browser. Beides schadet dem Auftritt, auch unabhängig vom Datenschutz.

Regelmäßig kontrollieren statt einmal einrichten

Weiterleitungen brechen oft unbemerkt: nach einem Hosting-Wechsel, einem Plugin-Update oder einer CDN-Änderung. Eine wiederkehrende Prüfung ist deshalb sinnvoll. Wer das Ergebnis seiner Prüfungen auch nach außen zeigen möchte, findet in unserem Beitrag zum Siegel mit Datum des letzten Checks Hinweise, was diese Anzeige aussagt und was nicht. Ein Siegel ersetzt allerdings weder die technische Behebung noch eine rechtliche Beurteilung im Einzelfall.

Fazit

Wenn die HTTPS-Weiterleitung nicht funktioniert, liegt die Ursache meist in einer fehlenden oder doppelten Regel, einem CDN-Konflikt, falschen CMS-Adressen oder eingebundenen HTTP-Inhalten. Testen Sie alle Adressvarianten, schließen Sie Caches aus und nutzen Sie nur einen Umleitungsmechanismus. So schließen Sie eine typische Schwachstelle, die aus Datenschutzsicht nicht unterschätzt werden sollte.
